### 9. Webhook subscription secret — stored in plaintext (2026-08-08)
- **What exists today:** `webhookSubscriptions.secret` (`src/db/schema/integrations.ts`) is generated randomly and stored as plain text, used to HMAC-sign every outbound delivery so a receiver can verify authenticity. It's never displayed back to the user after creation in the UI, but it IS readable in a raw database query/backup, unlike API keys (which only ever store a SHA-256 hash — see that table's own comment).
- **Why it wasn't silently "fixed":** encrypting it at rest needs a new server-side secret (e.g. `WEBHOOK_ENCRYPTION_KEY`, AES-256-GCM) that would have to be generated once and set in both `.env.local` and Vercel's Production environment variables — introducing a new required production secret isn't something to do without your sign-off, and getting it wrong (e.g. losing the key) would make every existing webhook secret unrecoverable, breaking live subscriptions.
- **To unblock:** say the word and this is a same-session addition — generate a key (`openssl rand -hex 32`), add it as `WEBHOOK_ENCRYPTION_KEY` locally and on Vercel, then encrypt on write / decrypt on read with a version-prefixed format (`enc:v1:...`) so existing plaintext secrets keep working until they're next rotated.
- **Status:** Low real-world severity today — this table isn't part of any known active exploit path, and the app's own database access is already restricted to the service role — but flagged rather than left undocumented.
